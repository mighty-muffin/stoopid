A Python package that starts out meaningless and is being turned into something
useful by AI agents. [GitHub Agentic Workflows](https://github.github.com/gh-aw/)
research and propose concepts, a human picks one, and the agents build it
through the same release pipeline a human would use. See
[`specs/0001-stoopid-design.md`](specs/0001-stoopid-design.md) for the pipeline and
[`specs/0002-ai-driven-development.md`](specs/0002-ai-driven-development.md) for
how the agents work.

## Install

```sh
pip install stoopid                      # latest release (PyPI)
pip install --pre --no-deps \
  --index-url https://test.pypi.org/simple/ stoopid   # latest dev build (TestPyPI)
```

## Usage

```console
$ stoopid add 1 2
3
$ stoopid mul 3 4
12
$ stoopid fib 10
55
```

```python
>>> import stoopid
>>> stoopid.fibonacci(10)
55
```

## Use as a dependency

```toml
# your project's pyproject.toml
[project]
dependencies = ["stoopid>=0.1"]
```

A runnable example project lives in [`examples/consumer/`](examples/consumer/).

## How stoopid evolves

1. **concept-research** (weekly) files 3–5 `concept:proposal` issues for
   developer-tooling CLIs, each scored on demand, gap, buildability and
   whether it works without a paid API.
2. A maintainer adds **`concept:accepted`** to one. **planner** opens a draft
   PR with the concept's spec and files roadmap issues.
3. A maintainer adds **`agent:ready`** to the issues worth building. **builder**
   (weekdays) takes one at a time and opens a draft PR, test-first. Comment
   `/fix <notes>` on it to request changes.
4. A maintainer reviews and squash-merges. Agent PRs never auto-merge.
5. **improver** (weekly) files improvement issues, which go back to step 3.

Workflow sources are `.github/workflows/*.md`; the `*.lock.yml` files next to
them are generated by `gh aw compile`.

## How releasing works

1. Every PR title must follow [Conventional Commits](https://www.conventionalcommits.org/)
   (`feat: …`, `fix: …`, `feat!: …`, `chore: …`). PRs are squash-merged, so the
   title becomes the commit on `main`.
2. On each push to `main`, [release-please](https://github.com/googleapis/release-please)
   keeps a **release PR** open with the next version and the `CHANGELOG.md` entry.
   Until 1.0: `feat!` → minor, `feat`/`fix` → patch.
3. The same push publishes a dev build `X.Y.(Z+1).devN` to TestPyPI.
4. **Merging the release PR** tags `stoopid-vX.Y.Z`, creates the GitHub Release, builds
   once, publishes to TestPyPI, smoke-tests the install, then publishes to PyPI
   (Trusted Publishing + PEP 740 attestations, no API tokens).
5. To force a version (e.g. 1.0.0), add `"release-as": "1.0.0"` to the package in
   `.github/release-please-config.json` through a PR, then remove it after the release.
6. If a release's publish fails, fix the workflow, then republish the existing
   tag: `gh workflow run release.yml -f tag=stoopid-vX.Y.Z`.

Dependencies, Actions and hooks are updated weekly by Renovate; non-major
updates merge themselves when CI is green.
